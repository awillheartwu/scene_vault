# 系统架构

## 组件边界

```text
Vue 3 UI
  │ Tauri invoke / events
  ▼
Commands（IPC 边界）
  ▼
Rust Services ─────► Filesystem / Thumbnail Cache / Python Process
  │
  ▼
SQLite
```

- `src/` 负责展示、交互和 invoke 客户端，不直接访问 SQLite 或任意文件路径。
- `src-tauri/src/commands/` 接收参数并返回稳定的 IPC 模型，不承载业务规则。
- `src-tauri/src/services/` 负责事务、状态机、路径校验、处理队列和归档。
- `src-tauri/src/db/` 负责连接、迁移和 SQLite 基础设施。
- `python/` 是可选的单图处理引擎，不拥有主数据库，也不直接写 NAS。

主数据库位于 Tauri app data 目录；缩略图和处理中的派生产物位于 app local data 或
cache 目录。源素材保留在用户选择的位置。

## Capture Session

```text
游戏截图目录
  │ 轮询、稳定性校验、会话基线与内容去重
  ▼
capture_items(awaiting_label)
  │ 人工分类；person 选择主角色
  ▼
queued ──► processing ──► archive_pending ──► completed
              │                 │
              └─────────────────┴──────────► failed / retry
```

项目可以配置多个启用的来源目录。开始会话时，Rust 快照每个来源中已有图片的规范路径、
大小和修改时间；之后只忽略身份仍未变化的旧文件。相同内容通过哈希去重，不会因来自
不同目录而重复导入。

截图先进入待分类状态：

- `person`：必须选择主角色；视觉引擎可用时处理，否则降级为原图归档。
- `scene` / `private`：跳过 Python，原图进入对应目录。
- `unclassified`：不处理、不归档。

人工选区、撤销分类和后台识别会同时作用于同一张图片，因此每张图片都有独立的串行锁：
`capture_operation_service` 提供按图片加锁、读写 `processing_version` 和
`operation_owner` 占用检查。识别结果写回前必须校验源文件内容身份和本次处理版本，
撤销分类在取得所有权后执行，迟到的结果被拒绝而不是覆盖新状态。

人工框选的主脸保存在 `manual_face_roi_json`，与检测框和可再生的特征分开；特征提取
和最终图片处理都接受可选的归一化选区，未提供时保持自动主脸行为。撤销分类通过预览、
执行和进度查询三组接口完成：预览把名单和每个文件的身份快照冻结在进程内存里，执行逐张
串行清理并校验文件身份，任务不落库、不排队，应用重启后重新发起即可。

## 截图文件身份与生命周期

源文件和归档目标是两类独立的文件引用，数据库分别记录其状态：
`available`、`missing`、`replaced` 和 `unavailable`。应用永远不删除原图；已经归档过的源
文件消失时标记 `missing` 并保留 Capture Item，尚未归档且从未形成可用结果的项沿用受状
态保护的清理规则。任何处理、重新识别、重试或重新归档开始前，都必须重新验证源文件内容
身份，避免把同一路径下后来替换的文件写入旧记录。

后台扫描对已知原图先使用文件大小和修改时间的快速路径；人物工作台的“检查项目文件”会
强制重算项目全部已知原图的内容哈希，并同时核对归档目标及头像目标的状态。旧路径缺失时，
只在当前启用来源目录中找到唯一的“同文件名且同内容哈希”候选后更新路径；歧义候选不猜测，
来源目录不可访问时不批量改写缺失状态。检查不登记无关文件，也不启动识别。相同路径出现新内容哈希时
创建新的 Capture Item，并将旧历史记录标记为 `replaced`；同一项目中已经删除过的内容哈希
会写入忽略表，之后再次出现仍保持忽略。已有截图导入列表过滤这些内容，确认导入时再
检查并跳过，避免一个已忽略文件中断整批正常登记。忽略记录保留用户的移除决定，不因
原图仍在目录里或临时缺失就自动清理；它不授权删除原图。不同项目仍可独立记录相同内容。

删除单张 Capture Item 或人物时，可选择删除归档目标，界面默认勾选。原图始终保留；选中
删除目标时，本地 Windows 目标文件只能移动到回收站，不能在回收站失败时回退为永久删除；
UNC/NAS 目标在界面明确二次确认后永久删除。目标已不存在视为删除完成；部分目标删除失败时保留全部数据库记录，并报告
失败项，后续可重试且只处理尚未完成的目标。只有删除记录的事务完成后，与记录关联的本地
派生图和缩略图才会永久清理；这些派生文件不进入回收站。

## Python AI 协议

Rust 通过版本化 JSON 协议调用常驻 Python `worker`，以 JSON Lines 串行处理多个请求
并复用 YuNet、SFace 和 ArcFace 模型实例。Worker Manager 在第一次视觉请求时惰性
启动并完成健康握手；设置变化、进程退出或传输错误会终止旧进程，下一请求重新启动。
当前请求遇到 worker 超时或崩溃时，在确认旧进程已停止后降级到一次性 `request`，避免
截图任务丢失。两种模式的标准输出都只能包含机器可读响应，日志和带 `SVPROGRESS`
前缀的阶段进度写入标准错误；Rust 将进度转发为 Tauri 事件。

```text
Rust AI Service
  │ processScreenshot（绝对本地路径）
  ▼
Python Provider
  ├── YuNet 人脸检测
  ├── 名字标注与头像裁剪
  └── SFace / ArcFace 特征提取
```

Python 每次只处理 Rust 指定的一张图片及本地输出路径。它不扫描来源目录、不读取角色
名单、不修改 SQLite，也不把半成品写到 NAS。`processScreenshot.payload` 支持可选的
归一化 `faceRoi`：Rust 的特征提取与最终图片处理都传入同一选区，省略时保持自动主脸行为。
另有 `roi` 组（`expandRatio`、`multipleFaces`）控制框选时的扩边重试比例与多脸处理策略，
省略时保持引擎默认（0.15 与报错）。
协议字段、约束和错误码见 [Python AI 协议](../python/README.md)。

Worker 由全局 single-flight 管理器拥有，不与 `capture_items` 状态机竞争任务所有权。
应用退出时先取消活动请求并关闭 stdin，短暂等待后仍未退出才强制终止子进程。

## 本地日志与诊断

Rust 的 `log_service` 是运行日志的统一入口。日志按 JSON Lines 写入 Tauri 应用日志目录，
使用 `debug`、`info`、`warn`、`error` 四个等级和稳定的模块名。Python 标准错误中的非进度
信息由 Rust 归入 `vision.python` 模块；Python 不直接管理桌面应用日志文件。业务线程只向
有界队列提交记录，独立日志线程负责写盘；队列满时丢弃单条日志，不阻塞截图处理。

单个日志文件达到 5 MiB 后轮转，归档文件保留 14 天且最多 20 个。清理在启动、轮转和
用户手动触发时执行。History 调试日志查看器通过只读 Tauri Command 查询最近记录，查询
上限为 1000 条；诊断摘要只汇总运行环境和最近 24 小时的警告、错误，不读取数据库业务
内容。性能打点（图片读取、归档缩放、扫描、AI 请求耗时）默认写入独立的 `logs/perf/`
文件，可在日志策略里整体关闭。

性能通道还记录前端图片解码/显示就绪、归档准备/复制/校验/重命名及整次保存耗时。
后台资源监控复用 Rust Windows API，每 60 秒采样进程树，每 5 分钟只读核对应用缓存
与数据库体积，放在独立阻塞任务中串行执行；不扫描游戏目录、模型或用户素材库。
后台 CPU 基线与前台资源页独立，关闭性能日志同时停止后台采样，退出时取消后续任务。
各阶段和采样结果由现有 PowerShell 分析脚本读取，产品不调用 PowerShell 来采集资源。

OCR、Caption 和通用 Embedding Provider 仍是未来能力；现有 Provider 抽象应允许它们
独立加入，但当前文档不得将其描述为已实现。

## Face Bank 与模型隔离

人工确认的 `person` 截图可以将主脸特征登记到角色样本库。新截图的主脸特征只与同一
项目、相同 `model_id`、`model_version` 和维度的活跃样本比较；阈值和第一/第二名
margin 共同决定是否产生建议。建议不会直接改变主角色，必须由用户确认。

特征是可再生派生数据：重处理或重建时先取得完整新结果，再在事务中原子替换。无脸、
低质量、缺少模型身份或角色改判时删除不再成立的旧样本；启动失败或超时等“没有得到
新结论”的错误可以保留旧样本，并显式报告其状态。

重建样本库只重算特征，不改变截图的 `character_id`；新样本继续登记到截图当前绑定的
角色。重建完成后，已有可用特征的待分类截图会按当前阈值和 margin 重新计算建议，旧的
Face Bank 建议如果不再通过门槛会被清除。

单张「重新提取人脸特征」沿用同一语义：只重算一张截图的特征，按当前角色重登记样本并刷新建议，不生成标注/头像、不重新归档，也不改变分类或角色绑定；处理中（queued/processing/archive_pending）以及 scene/private 截图会被拒绝。

识别器可在 SFace 与 ArcFace 间切换。不同模型的 embedding 空间不可比较；切换模型后
旧样本保持可追溯但不参与匹配，用户可在工作台重建 Face Bank。ArcFace 权重由用户
自备，不随应用分发。模型版本包含权重文件内容指纹，因此同一路径下替换权重也会触发
模型重载并隔离旧样本；指纹按规范路径、文件大小和修改时间缓存，人物工作台异步刷新
兼容状态，不用模型文件哈希阻塞人物与截图首屏；替换后需要重建 Face Bank。阈值与效果以
[BENCHMARK.md](BENCHMARK.md) 为准。

当前产品仍采用“一张人物截图 = 一个主角色”。`capture_faces` 支持一张截图关联多张脸，
但当前只写主脸并只对主脸给建议；多人逐脸确认和多角色素材关联留待真实需求出现。

## 归档与改判

Python 输出先写本地缓存。Rust 校验后执行：

```text
本地结果 → 目标目录临时文件 → 大小/内容校验 → 原子重命名
```

NAS 离线或复制失败时保留本地结果和持久化状态，通过退避和人工重试继续。应用重启会
恢复待归档任务；处理中断会记录失败，避免无界循环。

归档标注图与头像分别在 `capture_archive_fingerprints` 保存已校验的 SHA-256。复用、临时
副本校验和重命名结果确认均比较内容；同路径替换还要求当前目标匹配已记录的旧指纹且
不被其他截图或项目共享。缺少可信指纹的旧目标不自动认领，保留文件并提示使用新的
目录或命名重试；换名后的旧目标清理同样检查身份，UNC/NAS 不自动永久删除。

缩略图缓存包含源文件指纹、变体的生成版本及缩略图自身的哈希。原图版本不随归档改变，
标注/头像随处理结果改变，归档图随归档结果改变。旧版无可信关联的缓存按需重建一次，
不以时间戳认领，也不启动全库预计算；已挂载图片通过共享事件订阅刷新。生成并发为
“后台处理并行度”的值（1–32），调整限制时计入现有任务，降低后等待现有任务释放。
Rust 缩略图与归档图片的解码、缩放、编码在共享 Rayon 线程池中执行，Python/OpenCV
请求使用同一并行度设置；修改后新任务使用新设置，运行中的任务保留原线程池直到结束。
构建工具的 CPU 0–9 亲和性属于本机运行约定，与后台处理设置和 Cargo job 数分别管理。
开发入口显式标记应用在启动时恢复系统 CPU 范围，使 dev/release 的后台处理范围一致；
界面、数据库和 WebView2 不受后台并行度控制。

已完成截图被改判角色或分类时，Rust 重新入队处理并保留旧归档引用。只有新归档成功
后，才将旧归档文件移入 Windows 回收站并删除旧资产关系；回收站不可用时旧文件安全保留。进行中或待归档项拒绝改判，避免两个流程同时拥有
同一记录。

归档图可以配置输出尺寸：全局默认 + 项目继承或覆盖，作用于原图直存副本、标注图和头像
（PNG/JPEG，永不放大）。`capture-output` 中间产物超过体积预算时，已归档且超过保留期的
本地缓存会被自动清理，阈值与保留天数可在设置中调整或关闭。

## 项目笔记

项目笔记内容以 SQLite 为本地工作副本，后台任务把它同步到项目归档目标目录中的
`笔记.md`。写入采用临时文件、校验和原子替换；目标离线时持续保留本地状态，检测到
外部修改时先生成时间戳备份。笔记同步与截图归档共享“本地先完成、远端可恢复”的原则。

## 路径与安全约束

- Windows 正式配置保存 `D:\...` 或 UNC 路径，不保存 WSL `/mnt/...` 路径。
- `canonicalize` 可能产生 `\\?\` 前缀；路径包含校验前必须规范化。
- Python 拒绝 URI、相对路径、UNC 输入和 Windows device namespace，只接受明确的
  本地输入/输出路径。
- SQLite 启用 foreign keys、WAL 和 busy timeout。
- 扫描发现源文件消失时标记 `missing`，不直接删除用户记录。
- 所有结构变化通过追加迁移完成；已执行迁移不可修改。

## Ren'Py 引擎适配（可选）

- 添加截图来源目录时自动检测 Ren'Py 游戏（`game/` + `renpy/` 结构）并安装插件；检测冲突
  时可以手动指定目录。一个项目可以同时安装多个游戏，安装新游戏不影响已有安装。
- 插件由 `game/00_scenevault_bridge.rpy` 与 `game/scenevault_bridge.json` 两个文件组成，
  安装清单记录文件哈希；卸载只删除清单能证明归属的文件和编译产物。
- 游戏保存截图后，插件把说话人、对话、可见 tag、虚拟/物理分辨率写进应用缓存（每个安装
  一个 `install-<id>` 子目录）；截图入库时按来源路径找到所属安装，读取后立即删除缓存
  文件。游戏目录不留 JSON，不同安装之间也不会串数据。
- 说话人和视觉建议都会进入捕获页与分类弹框：视觉匹配是主要依据；说话人匹配是次要依据，
  没有视觉建议时用来预选，两者指向同一角色时标注「说话人匹配」并自动选中；说话人还没有
  对应角色时可以直接创建。
- 首页和捕获页都能启动游戏：优先选与游戏目录同名的可执行文件，有多个候选时在捕获页
  列出让用户选择；只拉起游戏进程，不注入、不等待。

## 后续扩展边界

通用素材扫描需要支持多根目录、增量扫描、取消、进度、符号链接保护、类型识别和
缺失标记。OCR、描述、Embedding 和语义搜索必须继续保持可选 Provider，不得让网络、
模型或 Python 成为读取素材库的前置条件。
