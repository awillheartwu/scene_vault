# 特写大脸检测与归档身份决策

日期：2026-10-05

## 背景

4K 级游戏截图里的特写镜头，人脸在原图中可达 1100 px 以上。YuNet 在“输入等于原图
尺寸”时覆盖不了这么大的脸，会退化成在眼部区域各自触发：同一张脸返回两个碎片框，或
只返回半脸框。表现是框选报“选区内检测到多张脸”、自动路径静默保存半脸框，头像、
标注和特征都来自错误的框。全库扫描（人物图、已存框置信度 < 0.85 的 406 条候选）确认
该现象普遍存在，与游戏无关，只是特写密度高的作品更集中。

## 决策

### 检测：双跑对比 + 按图强制

- `processScreenshot.payload` 新增可选分组 `bigFace`：`mode`（`off` 默认 / `auto` /
  `normalized`）、`minImageSide`（默认 1600）、`minFaceSize`（默认 600）。省略分组
  时保持历史行为；协议版本仍为 `1`。
- `auto` 先按原尺寸检测，再对长边缩到 512 的副本检测并映射回原图；只有满足“最佳框
  最小边 ≥ `minFaceSize`、面积 ≥ 原尺寸最佳框的 1.5 倍、置信度不低于原结果 − 0.05”
  才采用缩小结果。缩小为空保留原结果，原结果为空采用缩小结果。
- `normalized` 为手动强制：只用缩小检测、不回退原尺寸。
- 按条目持久化 `capture_items.face_detection_mode`（迁移 `0023`）：框选工具里的
  「整脸优化」按钮切换并随该图保存，重处理与归档沿用；撤销分类恢复 `auto`。
- 标注、头像和特征始终使用原图坐标，清晰度按映射回原图的框在原图上重新计算。

### 批量修复：先核对，再重排

- 人物工作台「更多操作 → 项目维护 → 修复大脸框」：先由数据库筛出低置信度脸框与
  缺少旧框的人物图，再用引擎逐张只读探测；确认碎片/半脸框的重新排队走完整处理，
  其余不动。
- 修复只允许单任务运行，状态携带 `projectId` 与 `taskId`：其他项目在跑时明确提示，
  不冒领进度；完成、部分失败、失败三态如实展示原因。
- 归档阶段冲突（目标被外部改动、缺少可信指纹）只影响该条目并如实报告，不静默覆盖。

### 归档身份：内容哈希，历史目标不自动认领

- 每次成功写入或复用归档都会在 `capture_archive_fingerprints`（迁移 `0024`）记录目标
  的 SHA-256；同路径替换要求当前目标匹配已记录的旧指纹，且目标不被其他截图或项目共享。
- 历史归档没有指纹时：先用仍然存在的本地标注图/头像与目标逐字节比对证明归属，一致
  才补记指纹；证明不了身份时保留旧文件，修复结果写到 `<原名> - repaired-<短ID>`
  （同一条目重试复用同一名字）。源文件始终不被改动。
- 长度相同不再作为“已经是同一张”的依据；`{seq}` 命名占用判断同样要求内容一致。

### 缩略图：内容指纹缓存与有限并发

- 缓存旁挂 JSON 指纹（源文件大小/时间/首尾采样 + 派生图生成代际 + 缩略图自身哈希）；
  标注图/头像/归档图被替换后自动重算，旧版无可信关联的缓存在需要时认领一次并补记
  指纹，不触发全库重编码。
- 生成并发跟随「限制图片处理时的核心数」，限制在 1–4 路；已挂载图片通过共享的
  `capture:item-updated` 订阅刷新，仅在文件身份真正变化时重取。

## 边界与不变量

- 源截图永不修改；归档只在能证明身份时原地替换，否则保留原文件。
- 自动识别仍然只提供建议，人工决定最终结果；批量修复只重排受影响的条目。
- `faceRoi` 与 `bigFace` 均为可选参数；不传时引擎行为与历史版本一致。

## 验收

- 真实样本 160 张新旧对比：58 张碎片/半脸框变为整脸框、10 张原报错变为成功、7 张原
  找不到脸现在可检出；其余与旧行为一致。
- WIAB 批量修复后 153 张全部 `completed`，归档无失败。
- 测试：Rust 285、前端 288、Python 127 全部通过；类型检查与生产构建通过。
