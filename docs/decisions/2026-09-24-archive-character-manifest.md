# 归档人物清单（project.json）决策

日期：2026-09-24

## 背景

评分插件直接扫描归档目录（例如 `0096_U4IA/人物图`）并把文件分组成人物的打分单元。
分组依赖文件名约定 `screenshot<序号> - 人物 - 哈希`；一旦采集端的原图命名不同
（例如 `u4ia_0001.png` 经模板 `{source} - {character} - {id}` 归档成
`u4ia_0001 - 亚伦 - 631cd9c5.png`），插件就会退化，把每张图当成一个独立人物。

放宽插件解析只是兼容手段，仍然解决不了这些情况：人物名里含 `-` 被截断、同一场次里
混用多种命名、人物改名后文件名与角色不再一致、人工调整过目录结构。因此由采集端输出一份
显式的人物 ↔ 图片映射，让消费者不必再猜。

## JSON 格式（v1）

Scene Vault 在被扫描的归档目录里写一个 `project.json`：

```json
{
  "version": 1,
  "kind": "scenevault.character-manifest",
  "generatedAt": "2026-09-24T10:31:22.418Z",
  "generator": { "name": "Scene Vault", "version": "1.0.11" },
  "project": { "id": "80893a8f-...", "name": "U4IA", "directory": "人物图" },
  "files": [
    "u4ia_0001 - 亚伦 - 631cd9c5.png",
    "u4ia_0002 - 安娜 - d40a1207.png"
  ],
  "characters": {
    "亚伦": ["u4ia_0001 - 亚伦 - 631cd9c5.png", "u4ia_0003 - 亚伦 - a1eaff85.png"],
    "安娜": ["u4ia_0002 - 安娜 - d40a1207.png"]
  },
  "entries": [
    {
      "file": "u4ia_0001 - 亚伦 - 631cd9c5.png",
      "captureItemId": "631cd9c5-...",
      "characterId": "6f5f...",
      "characterName": "亚伦",
      "classification": "person",
      "sourcePath": "D:/.../u4ia_0001.png",
      "contentHash": "…",
      "fileSize": 4716264,
      "archivedAt": "2026-09-09T06:00:00.000Z"
    }
  ]
}
```

字段约定：

| 字段 | 含义 | 消费者是否需要 |
| --- | --- | --- |
| `version` / `kind` | 契约版本与类型标记，便于以后演进 | 建议校验 `version == 1` |
| `generatedAt` | 该映射最后一次实际写入的时间（内容未变时不刷新） | 可忽略 |
| `generator` | 生成方与版本，排障用 | 可忽略 |
| `project` | 项目 id、名称、本清单位于哪个子目录 | 可忽略 |
| `files` | 展示顺序（相对本目录的文件名数组） | 用于排序 |
| `characters` | 人物名 → 文件名数组；键是人物显示名，值是该人物的文件 | **分组主依据** |
| `entries` | 逐文件明细，含采集记录 id、角色 id、来源路径、内容哈希 | 可忽略，留给后续功能 |

约束：

- 清单**始终位于被扫描目录内**，因此 `files` 里的条目就是该目录下的文件名（basename），
  不含上级路径；`characters` 的键值是同一个 basename。
- 未知字段必须容忍；未来只会追加字段，不改变既有字段语义。
- 未列在 `characters` 里的文件退回插件原有的文件名规则；未列在 `files` 里的文件排到最后。
- 清单只描述**磁盘上确实存在**的文件：目录里没有的文件不会出现，也不会留下幽灵条目。
- `project.json` 本身在插件忽略列表里，不会成为候选。

## 生成时机与更新策略

清单是派生数据，数据库是唯一事实来源，因此**每次都是全量重算**，不做增量补丁：

- 归档人物图成功后（`capture_archive_service`）：只按项目标记待重建，不立即写盘。
- 项目文件检查重定位归档目标后（`project_file_reconcile_service`）：路径变化会影响清单，重新标记。
- 角色改名或合并后（`character_service`）：人物显示名变化会影响 `characters` 键，重新标记。
- 撤销分类/回退后（`capture_reset_service`）：记录不再有归档目标，清单需要移除对应条目。
- 应用启动时：只补齐**缺失**的清单（老库升级、清单被手工删除），不做全量扫描。
- 手动入口：工作台的「更新评分清单」按钮，用于任何人工调整后的强制刷新。

写入由后台任务完成，并有 10 秒静默窗口：一批归档只会触发一次写盘，避免 NAS 抖动。
内容与磁盘上已有清单一致时直接跳过，所以静默窗口过后即使重复触发也不产生写操作。

## 配置

只有一个全局开关：`设置 → 通用设置 → 自动维护评分清单`（默认开启）。

- 开启：归档完成、项目文件检查找回、归档目录变更、角色改名/合并、撤销分类、删除已归档记录
  之后都会自动重建清单，启动时还会补齐缺失的清单。
- 关闭：以上自动路径都不写盘，已经排队的重建请求会被丢弃（而不是等你重新打开后集中回写）；
  人物工作台的「更新评分清单」仍然可以手动写入。
- 关闭不会删除任何已有清单；重新打开后由下一次触发或手动操作刷新。

## 增删改覆盖

清单是数据库的派生视图，所有变更都靠"整份重新生成"收敛，触发点如下：

| 变更 | 触发点 | 结果 |
| --- | --- | --- |
| 新增归档人物图 | `capture_archive_service` | 新文件进入 `files` 与 `characters` |
| 归档目录改名/搬迁后找回 | `project_file_reconcile_service` | 路径更新后按新文件名重写 |
| 修改项目归档目录 | `project_service::set_destination_directory` | 在新目录重建清单 |
| 角色改名 / 合并 | `character_service` | `characters` 键更新为新名字 |
| 撤销分类 / 回退 | `capture_reset_service` | 该条移出清单；目录里再无归档文件时删除清单 |
| 删除截图（含人物级联删除） | `capture_deletion_service` | 被删条目移出清单；目录里再无归档文件时删除清单 |
| 重新归档（重跑 / 改判） | `capture_archive_service` | 按新的归档文件名重写 |
| 读取归档图时发现文件已不存在 | `commands::capture::readable_capture_path` → `capture_service::note_destination_state` | 该条在下一次重建时移出清单 |
| 会话级「检查文件」发现归档目标出现/消失 | `capture_discovery_service::reconcile_files` | 状态变化后重建 |
| 项目级「检查项目文件」 | `project_file_reconcile_service` | 无论是否发生重定位都会重建 |

重建时只列**磁盘上确实存在**的文件，所以即使某条变更漏了触发，下一次触发或手动点按就会
把幽灵条目剔除；如果归档目录里已经没有对应的归档文件，清单会被删除而不是保留旧内容。

刻意不触发的环节（它们不影响清单内容）：缩略图缓存清理只切换 `annotated_path` /
`avatar_path`、识别设置变更只清理建议、人物头像设置只写 `avatar_asset_id`。
另外重新处理期间条目会短暂离开 `status = 'completed'`，因此可能临时不在清单里，
归档完成后由归档触发重新写回。

## 写入与容错

- 先在同目录写临时文件 `.project.json.<uuid>.partial`，校验长度后原子重命名覆盖；
  失败时删除临时文件并保留旧清单，绝不出现半截 JSON。
- 归档目录不可访问（NAS 离线、盘符没挂上）时跳过并计数，等下一次触发重试；不影响归档本身。
- 清单写入失败不会回滚或重试归档操作：归档文件已经校验落盘，清单只是附加元数据。
- 相关日志统一在 `capture.manifest` 模块下，事件 `archive_manifest_rebuilt` /
  `archive_manifest_write_failed` / `archive_manifest_remove_failed` /
  `archive_manifest_rebuild_failed`，错误码 `archive_manifest_*_error`。
- 目录里已没有可描述的归档文件时删除残留清单，避免消费者照着旧清单找不存在的图片。

## 边界与不变量

- 只为项目归档根下**规范的四个目录**里的 `人物图` / `人物图（原图）` / `人物图（未识别）`
  写清单；用户自建的暂存目录（例如 `zancun1`）不会被写入，也不被描述。
- 不移动、不重命名、不删除任何归档图片；清单只描述现状。
- 一个目录一份清单，不聚合跨目录内容，消费者扫描哪个目录就读哪份。

## 消费者侧（交接给插件实现方）

1. 扫描开始前读取被扫描目录下的 `project.json`；文件不存在、JSON 非法或 `version` 未知时
   完全退回现有文件名规则，不报错中断。
2. 人物归属优先取 `characters` 里该文件名的映射；未命中的文件再走
   `screenshot<序号> - 人物 - 哈希` 解析，最后才退化为文件名。
3. 展示顺序优先取 `files`；`files` 里没列到的文件按原有自然排序排在后面。
4. 单个人物可能有多张图，合并发送/每条最多 N 张的行为保持现状。
5. 验收：U4IA 的 `人物图` 目录生成清单后，面板预检人物数为 41（吉妮瓦 6 张、
   蒂根/奈克特拉/塞拉斯汀/奈娅各 4 张），报告 `data.json` 的 `characters` 长度为 41。

## 后续可选

- 每个项目一个「是否输出评分清单」开关（当前所有项目都会写）。
- 清单里补充人物排序权重或剧集信息，等评分流程提出需求再加。
